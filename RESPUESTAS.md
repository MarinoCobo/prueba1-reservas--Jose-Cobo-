## Riesgo más grave del repositorio

El archivo de configuración contiene una clave JWT con rol `service_role` (`lib/data/supabase_config.dart:4`), y el README recomienda usar esa clave (`README.md:20`). Al estar subida al repositorio público, expone una credencial privilegiada y viola la regla de no incluir secretos en el repositorio (`.specify/memory/constitution.md:17`). La migración activa Row Level Security (`supabase/migracion.sql:14`), que esa clave privilegiada puede saltarse (`lib/data/supabase_config.dart:4`, `README.md:20`).

## ¿La regla protege la app real?

No del todo. `lib/main.dart:14` crea `CrearReserva` y `lib/main.dart:26` la pasa a la pantalla. Aunque `lib/presentation/reserva_page.dart:9` declara el campo, la pantalla nunca usa `widget.crearReserva`; inserta directamente en Supabase (`lib/presentation/reserva_page.dart:60`). Esto contradice la regla de que la presentación use los casos de uso (`.specify/memory/constitution.md:9`, `.specify/memory/constitution.md:10`). La base solo declara la validación `fin > inicio` (`supabase/migracion.sql:11`), sin una restricción de exclusión para solapamientos.

Además, el caso de uso consulta las reservas en un paso (`lib/domain/crear_reserva.dart:17`) y las guarda después (`lib/domain/crear_reserva.dart:28`), sin atomicidad; dos solicitudes simultáneas podrían pasar ambas. La política de inserción permite cualquier fila a usuarios autenticados (`supabase/migracion.sql:21`, `supabase/migracion.sql:23`, `supabase/migracion.sql:24`); la pantalla envía el texto editable del ID como `usuario_id` (`lib/presentation/reserva_page.dart:62`, `lib/presentation/reserva_page.dart:89`, `lib/presentation/reserva_page.dart:90`), así que se puede reservar a nombre de otra persona.
